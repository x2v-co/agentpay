# Judge demo: threat model and deployment contract

This is a local implementation review and automated test record, not an independent
security audit or evidence of a deployed multi-user service. The original localhost
handoff and its delivered-order database remain untouched.

## Assets and trust boundaries

Protect signed payment payloads, per-session orders/reports, configured recipient,
settlement uniqueness and persistent pending state. Public saved Devnet evidence is
intentionally public and separate from current orders. No wallet key is held by the
service. The browser wallet and facilitator remain external trust boundaries.

Threats: malicious anonymous visitor, hostile website, forged/cross-session request,
replayed signed payload, malformed input, concurrent submissions, remote RPC failure,
process restart and configuration drift. The HTTPS edge, host administrator, database
and externally supplied high-entropy session secret are trusted. Host compromise,
wallet compromise, facilitator compromise and distributed denial-of-service are not
solved by this prototype.

## Implemented boundaries

- Separate `judge.ts` entry point; current `handoff.ts` is not exposed or rewritten.
- Network, mint and 1,000 atomic price remain constants. Recipient is pinned to the
  existing test merchant `s6gS82AnfUCib9emQjVVJPmxD6GwUQJF3hYeter2FR9`. Public configure
  calls can check the payer's ATA but cannot change recipient or network.
- Signed 24-hour `__Host-agentpay` cookie: Secure, HttpOnly, SameSite=Strict, Path=/;
  per-session CSRF bearer; no payment/session token in the judge RPC URL. The server
  creates only transient reviewer session identifiers, not deployment credentials.
- Owner mappings are durable and checked before every order GET, report POST and
  reconciliation POST. Foreign and absent IDs return the same 404. Guessing a payer
  address is not sufficient to access its orders. The owner is a browser session,
  not proof of a real-world identity or wallet ownership.
- Exact Host, exact Origin for all POSTs, cross-site Fetch Metadata rejection, CSP,
  no-referrer, no-store and nosniff. The SDK RPC uses the same-origin secure cookie
  plus exact Origin because its client does not attach custom CSRF headers.
- RPC method/parameter allowlist; no broadcast, faucet, simulate or arbitrary target.
  Readiness uses public endpoints only. An explicit signed payment POST is the only
  route that can invoke settlement.
- SQLite-backed limits survive restarts: 120 API requests/minute globally, 60 per
  session/minute, 20 new sessions/minute globally, 5 quote attempts/session/hour,
  5 payment POSTs/session/minute, 10 reconciliations/session/minute, 30 RPC requests/
  session/minute, 6 account/capability checks/session/minute and 10 offline examples/
  minute globally. Forwarded client-identity headers are not trusted.
- Global lifetime cap of 1,000 quote attempts (including invalid ones) bounds order
  storage; reaching it fails closed and needs deliberate operator handling. This is
  not a billing quota, and public sessions cannot reset it. Per-payer existing
  payment reservations remain enforced by OrderStore.
- Original durable settlement claims, unique message/transaction constraints and
  pending-on-uncertainty are reused. No automatic re-settlement or replacement order.
- Reload with a known prior order blocks new judge quotes until that order is
  successfully recovered. Expired/lost cookies cannot recover through payer address
  alone; keep the original session and contact the operator if access is lost.
- Public `/evidence.json` serves the sanitized committed run only. Public offline
  examples use the actual report service with separate in-memory SQLite and mock
  facilitator/RPC; they never read live order storage or use the real gateway.

## Environment (values not generated by this task)

| Variable | Required value / purpose |
| --- | --- |
| JUDGE_ORIGIN | Exact externally served HTTPS origin, without trailing slash/path |
| JUDGE_SESSION_SECRET | Existing/operator-provisioned cryptographically random 32–64 byte secret encoded as 64–128 lowercase hex characters; no fallback; never use the public test fixture |
| JUDGE_DB_PATH | Absolute path on a durable single-host disk, e.g. `/var/data/agentpay/judge.sqlite`; separate from the local handoff DB |
| PORT | Valid service port, default 4032 |
| JUDGE_LISTEN | Omit to bind localhost behind a local HTTPS proxy; `platform` deliberately listens on available interfaces behind the platform HTTPS edge |

No RPC key, facilitator key, wallet seed or merchant signing key is configured.
The supplied secret is not stored; only its fingerprint is saved to detect unsafe
configuration changes. Restart must retain secret, origin, recipient and database.
Changing these refuses startup; rotation/migration needs a deliberate design, not
silently opening old orders under a new session scheme. Do not log environment,
Cookies, Authorization, token URLs or PAYMENT-SIGNATURE request bodies.

## Tests and limits of evidence

Final local run: **93/93 tests in 8 files**, including 14 judge tests; both existing
smoke checks, full and Solana type checks, build and compiled judge smoke passed.
Trusted hydrated dependency snapshot was used to avoid macOS placeholder I/O; all
changed inputs were copied before this run. No new dependencies were added.

`tests/solana-judge.test.ts` uses a mock facilitator/RPC and loopback HTTP with an
explicit HTTPS virtual Host/Origin. It tests session isolation on all order routes,
CSRF/cookie mismatch, merchant immutability, host/origin checks, broadcast rejection,
failed verification/no report, concurrent single settlement, pending timeout across
restart, durable quotas, session churn/expiry/tampering, configuration mismatch,
malformed/tampered payment, unavailable readiness and independent offline examples.
The built-output smoke test serves real compiled assets and committed evidence and
runs examples while asserting zero calls to the real test gateway's settlement.
Existing wallet tests cover signing decline, altered transaction/quote and signed
message validation. No new wallet operation or real payment was performed.

Browser behavior behind a real TLS proxy, actual Secure-cookie handling, deployment
persistence, platform request limits and a new live wallet flow remain untested in
this local task. Do not label the automated checks an independent audit.

## Residual risks and operator requirements

- Anonymous users can consume global limits or deliberately fill the finite order
  capacity. Limits bound resource use, not availability. A judge access gate and
  platform-level rate limiting are recommended before public exposure.
- Payer public keys are not authenticated before quoting. A hostile visitor can
  temporarily reserve another payer's quote budget until the 120-second expiry.
  It cannot sign for that payer or read its orders. Wallet ownership challenges
  would be an additional feature; do not call the quote endpoint identity-verified.
- A lost/expired session fails closed. Pending orders and reservations remain in the
  DB; operator-only recovery must verify evidence without creating a new payment.
  Do not delete the DB or reset limits to resolve ambiguous settlement.
- One process/instance and durable SQLite volume only. Keep WAL/SHM with the DB,
  restrict filesystem access, and use SQLite-consistent backups. Do not roll back
  to a pre-payment DB snapshot: that can lose settlement claims and allow retries.
- Proxy must terminate valid TLS, preserve the configured Host and pass the original
  Origin unchanged. Do not expose the backend transport directly or weaken checks.
- The service has no production monitoring, incident workflow, user revocation or
  multi-device account recovery. Do not claim general production readiness.

## Hosting choices — proposals only

Free static GitHub Pages can serve a receipt viewer, presentation and prerecorded
video links, but cannot host this Node/SQLite payment service. Label such a site
read-only; it is not a substitute for a deployed live payment API required by the
form. Official: https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site

An already-owned persistent host with an existing HTTPS proxy may avoid incremental
hosting charges; availability, access and approved hostname have not been verified.
Do not expose the user's Mac or tunnel localhost as a substitute.

A paid single-instance Render web service plus persistent disk is a concrete option.
Render's default filesystem is ephemeral; persistent disks require a paid service,
are single-instance, and redeploys briefly interrupt service. Free ephemeral compute
is unsuitable for this payment ledger. Account, destination, cost cap and retention
must be approved before creating resources. Official: https://render.com/docs/disks
and https://render.com/docs/web-services . No pricing or free-tier availability
beyond those documented constraints is assumed.
