# AgentPay: Procurement for Autonomous Agents

## Submission Copy

**One line:** An agent can buy its next inference within an owner's spending rules, then recover its result and verify settlement on Monad.

Agents can write code, but access to more inference still often ends at a human checkout, a copied API key, or a subscription screen. AgentPay explores a smaller, executable alternative: buy one bounded inference through a machine-fulfillable offer.

The open reference implementation joins model information from aiplans.dev with Toolkit merchant offers. An owner-signed policy limits the wallet, merchant, model, asset, chain, expiry and spend. The SDK binds the request to a reservation, authorizes a ceiling using x402 `upto` and Permit2, and handles metered settlement and result recovery. A pending chain receipt stays pending; it is not presented as a completed purchase.

The public demo puts the judge in the owner's seat: commission a checkout repair, set a budget, choose autonomous procurement or approval first, reproduce a failing test, inspect an offer, follow historical payment evidence, and accept the local deliverable. A six-stage overview connects the decisions into one procurement loop. Quick preview is available without granting permissions or recording acceptance.

## What Is New Beyond x402?

| Layer | Role | AgentPay contribution |
| --- | --- | --- |
| aiplans.dev + Toolkit discovery | Product data and machine offers | Join comparable model records with eligible fulfillment routes; reject human-checkout offers |
| Owner policy | Delegated purchasing authority | Bind merchant, model, wallet, asset, chain, spend and expiry |
| Request reservation | Define what is being bought | Bind full request digest and token bounds to a purchase ID before execution |
| x402 `upto` + Permit2 | Payment protocol and bounded token authorization | Use existing standards rather than inventing a payment rail |
| Purchase lifecycle | Handle uncertainty | Preserve execution records for settlement retries, reconcile receipts, and recover purchase-scoped access |

The innovation claim is the procurement workflow and integration, not the invention of x402, Permit2, a new blockchain, or a universal subscription buyer.

## Why Monad?

Monad Testnet is the settlement network used in the recorded integration. The receipt validator checks an ERC-20 transfer against the expected payer, merchant, asset and metered amount. EVM compatibility lets the implementation use the existing Permit2 and x402 ecosystem.

The long-term opportunity is frequent, small machine purchases without a human checkout for each request. This submission does not claim measured latency, gas savings, throughput, mainnet readiness, or a unique requirement for Monad. The historical transfer amount is not the gas fee and is not a production model-pricing benchmark.

**New paid-repair acceptance, September 10:** purchase `e69e6208-2429-4f48-b2f3-5efd725e3dab` used OpenRouter `z-ai/glm-5.3-flash` to generate the checkout fix. Its unchanged output passed all three isolated browser tests. The same purchase consumed 131 input + 89 output tokens and settled 33 atomic test USDC (0.000033 USDC) within the 0.1 USDC ceiling. The operator independently matched the successful Monad transfer's payer, merchant, asset and amount. See the [evidence page](https://x2v-co.github.io/agentpay/live-repair.html), [raw bundle](../apps/demo/assets/live-repair.json), [merchant proof](https://staging.toolkit.fun/api/agentpay/v1/proofs/proof_083f233adf91dfe6) and [transaction](https://testnet.monadexplorer.com/tx/0x16be7f05d7a7fb045372ab3c2ff285a34cb5ad9e75603183858de6e1d20e7db3).

The new video reviews that completed run; it does not reenact signatures. This was operator-assisted, with owner-confirmed wallet signatures. Tests are owner-reported browser Worker results, not cryptographic execution attestations. The interactive simulation remains distinct from this real evidence.

**Not implemented:** autonomous salary earning, mainnet fund management, buying arbitrary Coding Plans, or bypassing a vendor's human checkout. Coding Plan listings are not token balances and are not machine-fulfillable simply because they are listed in a catalog.
